AP1で障害が発生し、AP2への切替が行われたという連絡を受けました。しかし、切替後も業務が正常ではないとの報告があります。まず、どの情報を調べれば状況を判断できるか考えましょう。

**調査の目的：コンテナの稼働・APの役割・業務の成否を分け、ログを根拠に次の調査対象を選ぶ。**

## 考える問題

1. AP1・AP2・DBの稼働状態をどう調べますか。AP2への自動切替は成功していますか。
2. 切替後の業務は成功していますか。役割の変化とは別の根拠を挙げてください。
3. 次にどこを調べますか。ログを根拠に調査対象と仮説を考えてください。

まず自分で調査し、判断の根拠をメモしてください。困った場合だけヒントを開きます。模範解答を開く操作だけではコマンドは実行されません。

<details>
<summary>ヒント1：Dockerで何を調べるか</summary>

コンテナの一覧は `docker ps`、APの記録は `docker logs` が手掛かりです。稼働状態・役割の変化・業務結果を別々に調べましょう。

</details>

<details>
<summary>ヒント2：オプションとログの絞り込み</summary>

一覧には停止中のコンテナも含めたいので、`ps` の `-a` オプションを調べます。`logs` では役割の記録を全体から探し、業務結果は `--tail` で最近の行を読みます。`grep` は該当行を探し、パイプ `|` は出力を次のコマンドへ渡します。`2>&1` は標準エラー出力を標準出力へ合流させます。役割を示す記録だけで業務回復と判断しないようにしましょう。

</details>

<details>
<summary>模範解答：自分で考えてから開く</summary>

以下のコマンドを上から順に実行し、自分の出力と説明を照合してください。コードの実行ボタンは自分で押します。見つからないログや未観測の状態を、確認済みとして扱わないでください。

### 1. コンテナの状態を見る

```bash
cd /root/lab
docker ps -a
```{{exec}}

`NAMES`列はコンテナ名、`STATUS`列は稼働状態を示します。AP1・AP2・DBの3台を探してください。

| 表示 | 意味 |
|---|---|
| `Up` | コンテナが稼働中。業務成功を保証する表示ではない |
| `Paused` | コンテナ内の処理が一時停止している |
| `Exited` | コンテナが終了している |

### 2. AP2への切替を確認する

まず、役割に関するログを探します。昇格の記録は過去の行にあるため、末尾の数行だけに絞りません。

```bash
docker logs ap-server-2 2>&1 | grep -E 'starting as STANDBY|PROMOTED to ACTIVE'
```{{exec}}

`STANDBY`は待機系、`ACTIVE`は現用系です。どの役割からどの役割へ変化したか、自分のログから判断してください。

### 3. 業務ログを確認する

続けて、最近の業務ログを読みます。

```bash
docker logs --tail 30 ap-server-2
```{{exec}}

日時、ログレベル（`INFO`・`WARN`・`ERROR`）、メッセージに注目してください。繰り返し出ている行と、その説明を記録しましょう。過去の記録と直近の業務結果も区別します。

### 判断と技術的な解説

以下は想定する障害状態の模範解答です。引用は実装が出力するメッセージの固定部分です。日時や要求IDは実行ごとに異なるため、自分の画面のログと照合してください。記録が見つからない場合は、模範解答だけで成功・失敗を決めないでください。

### 問1：AP2への自動切替

**答え：AP2への自動切替は成功している。**

根拠となるログ：

> `ap-server-2: PROMOTED to ACTIVE (failover)`

この記録は、AP2が待機系から現用系へ昇格したことを示します。ただし、これだけでは業務が正常に処理されているかは分かりません。

### 問2：切替後の業務

**答え：一部の業務処理でDB接続失敗が発生しており、正常な業務継続は確認できない。**

根拠となるAP2のログ：

> `DB connection failed:`

実装ではこのメッセージに `ap-server-2:` という接頭辞は付きません。`docker logs ap-server-2` で取得したログであることと、続く `worker=`・`request_id=`・`detail=` を根拠に確認します。

`detail=` に次のPostgreSQLエラーが実際に含まれている場合は、その行も根拠として挙げられます（実行状況により文言は異なります）。

> `FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute`

これは一般ユーザーが利用できる接続枠に空きがないことを示す手掛かりです。なぜその状態になったのかは、このログだけでは判断できません。

一方、次の記録が混在する場合もあります。

> `job SUCCESS:`

これは業務成功の記録です。接続失敗があるからといって、すべての業務が失敗しているとは断定しません。過去の成功行だけで復旧と判断せず、昇格後の直近の成功・失敗を確認してください。

### 問3：次の調査対象

**答え：次に調べるべき対象はPostgreSQL（db-server）である。**

根拠は、AP2のログに `DB connection failed:` が記録されていることです。DB接続に問題がある可能性が高いため、DB側の接続状況と設定を照合します。接続枠不足なのか、なぜ接続が残っているのかは、Step 2で調査します。

### まとめ

AP2は `PROMOTED to ACTIVE` のログから自動昇格に成功したと判断できます。一方、`DB connection failed` のログが出力されており、切替後の一部の業務処理は失敗しています。したがって、APの切替は成功していますが、業務が正常に復旧したとは判断できません。次はPostgreSQLの接続状況と設定を調査します。

## CHECK前の確認

- AP1、AP2、DBそれぞれのコンテナ状態を確認した。
- AP2の昇格ログを確認した。
- 直近のログから業務の成否を確認した。
- 3つの問いに、ログを根拠として答えられる。

このStepのCHECKは、AP1がpause状態、AP2とDBが稼働中であることを判定します。ログからの読み取りは、自分でも確認してから進んでください。

CHECK後はStep 2へ進み、ログから選んだ調査先の接続状況を調べます。
