AP1で障害が発生し、AP2への切替が行われたという連絡を受けました。しかし、切替後も業務が正常ではないとの報告があります。まず、どの情報を調べれば状況を判断できるか考えましょう。

**調査の目的：コンテナの稼働・APの役割・業務の成否を分け、ログを根拠に次の調査対象を選ぶ。**

まず自分で調査し、判断の根拠をメモしてください。困った場合だけヒントを開きます。各領域を開くだけではコマンドは実行されません。

<details>
<summary>調査・操作のヒント1：Dockerで何を調べるか</summary>

コンテナの一覧は `docker ps`、APの記録は `docker logs` が手掛かりです。稼働状態・役割の変化・業務結果を別々に調べましょう。

</details>

<details>
<summary>調査・操作のヒント2：オプションとログの絞り込み</summary>

一覧には停止中のコンテナも含めたいので、`ps` の `-a` オプションを調べます。`logs` では役割の記録を全体から探し、業務結果は `--tail` で最近の行を読みます。`grep` は該当行を探し、パイプ `|` は出力を次のコマンドへ渡します。`2>&1` は標準エラー出力を標準出力へ合流させます。役割を示す記録だけで業務回復と判断しないようにしましょう。

</details>

<details>
<summary>模範解答：実行コマンド・SQL（自分で考えてから開く）</summary>

以下を上から順に実行します。開閉だけでは実行されません。出力を確認し、次の操作が安全か判断してから各コードの実行ボタンを押してください。考察問題のヒントと答えは、各問の欄で個別に確認できます。

### 1. コンテナの状態を調べる

```bash
cd /root/lab
docker ps -a
```{{exec}}

`NAMES` は名前、`STATUS` は稼働状態です。AP1・AP2・DBを探し、結果を記録します。

### 2. AP2の役割に関する記録を探す

```bash
docker logs ap-server-2 2>&1 | grep -E 'starting as STANDBY|PROMOTED to ACTIVE'
```{{exec}}

`grep -E` は複数のパターンを検索します。役割の記録は古い行にある可能性があるため、検索前に末尾の行数を制限しません。時刻とメッセージを記録してください。

### 3. 最近の業務ログを読む

```bash
docker logs --tail 30 ap-server-2
```{{exec}}

`--tail 30` で直近の30行を表示します。ログレベル、要求ID、メッセージの詳細を読み、役割に関する記録と業務の記録を分けて比較してください。判断理由は後の各考察問題で確認してください。

## 考察問題

各問を自分で考え、必要な問の欄だけ開いてください。根拠は自分のログ・SQL出力と照合し、未観測の結果を確認済みと扱わないでください。

### 問1：AP2への自動切替は成功していますか。コンテナ状態と役割の記録を根拠に説明してください。

<details>
<summary>ヒントを見る（問1）</summary>

`STATUS`列と、AP2の役割が変わった時刻のログを照合します。業務結果の行とは区別してください。

</details>

<details>
<summary>答えを見る（問1：自分で考えてから開く）</summary>

**結論：想定する障害状態では、AP2への自動切替は成功しています。**

**根拠：** AP2のログに `ap-server-2: PROMOTED to ACTIVE (failover)` があることです。自分のログの時刻を確認してください。Dockerの一覧では `Up` は稼働中、`Paused` は処理の一時停止を示します。

**技術的な解説：** `STANDBY` は待機系、`ACTIVE` は現用系です。昇格ログは役割の変化の証拠であり、コンテナの `Up` 表示だけでは役割は判断できません。また、昇格だけでは業務が正常かは分かりません。該当ログがなければ、この結論を確認済みにしないでください。

</details>

### 問2：切替後の業務は正常に処理されていますか。直近の業務ログを根拠に説明してください。

<details>
<summary>ヒントを見る（問2）</summary>

同じ要求の `request_id` とメッセージを確認します。役割に関する行ではなく、業務の成功・失敗に関する行を探してください。

</details>

<details>
<summary>答えを見る（問2：自分で考えてから開く）</summary>

**結論：接続失敗の記録がある要求では業務を開始できず、正常な業務継続を確認できません。すべての要求が失敗したとは断定しません。**

**根拠：** AP2から取得した直近のログの `DB connection failed:` を確認します。実装ではこのメッセージにAP名の接頭辞は付きません。`worker=`・`request_id=`・`detail=` を照合してください。`job SUCCESS:` が混在する場合は成功した要求もあります。

**技術的な解説：** 接続失敗の記録と、業務成功の記録は別です。過去の成功だけで現在の復旧と判断せず、昇格後の時刻と要求ごとの結果を比べます。成功ログが見えないことだけでも、失敗の証明にはなりません。

</details>

### 問3：次に調べるべきコンポーネントはどこですか。ログを根拠に調査先と仮説を考えてください。

<details>
<summary>ヒントを見る（問3）</summary>

</details>

<details>
<summary>答えを見る（問3：自分で考えてから開く）</summary>

**結論：次の調査対象はPostgreSQL（db-server）です。**

**根拠：** AP2の業務ログに `DB connection failed:` があり、`detail=` にDB接続時の説明が記録されていることです。自分のログと照合してください。

**技術的な解説：** エラーが発生した接続先で、稼働状態・設定・接続状況を照合する方針が考えられます。この時点で原因まで確定したわけではありません。AP側の記録だけで決めつけず、Step 2でDB側の情報を調べます。

</details>

## CHECK前の確認

- AP1、AP2、DBそれぞれのコンテナ状態を確認した。
- AP2の昇格ログを確認した。
- 直近のログから業務の成否を確認した。
- 3つの問いに、ログを根拠として答えられる。

このStepのCHECKは、AP1がpause状態、AP2とDBが稼働中であることを判定します。ログからの読み取りは、自分でも確認してから進んでください。

CHECK後はStep 2へ進み、ログから選んだ調査先の接続状況を調べます。
