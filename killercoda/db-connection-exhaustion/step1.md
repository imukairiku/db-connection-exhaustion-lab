切替が行われたという連絡を受けました。まず「コンテナが動いているか」「どちらが現用系か」「業務が成功しているか」を分けて確認します。

**学習目標：AP切替の成功だけでは、業務の正常性を判断できないことを理解する。**

## 1. コンテナの状態を見る

```bash
cd /root/lab
docker ps -a
```{{exec}}

`NAMES`列で3台を探し、`STATUS`列を確認してください。

| 表示 | 意味 |
|---|---|
| `Up` | コンテナが稼働中。業務成功を保証する表示ではない |
| `Paused` | コンテナ内の処理が一時停止している |
| `Exited` | コンテナが終了している |

## 2. AP2の役割と業務を別々に調べる

まず、役割に関するログを探します。昇格の記録は過去の行にあるため、末尾の数行だけに絞りません。

```bash
docker logs ap-server-2 2>&1 | grep -E 'starting as STANDBY|PROMOTED to ACTIVE'
```{{exec}}

`STANDBY`は待機系、`ACTIVE`は現用系です。`PROMOTED to ACTIVE`は現用系へ昇格した記録です。

続けて、最近の業務ログを読みます。

```bash
docker logs --tail 30 ap-server-2
```{{exec}}

日時、ログレベル（`INFO`・`WARN`・`ERROR`）、メッセージに注目してください。繰り返し出ている行と、その説明を記録しましょう。過去の記録と直近の業務結果も区別します。

## 出力から考えること

- AP2への切替は成功していますか。判断の根拠となるログを挙げてください。
- 切替後の業務は成功していますか。役割のログとは別の根拠を探してください。
- どこに問題がありそうですか。ログを根拠に、次に調べる対象と仮説を1つ挙げてください。

<details>
<summary>ヒント1：確認する情報を分ける</summary>

コンテナの稼働状態はDocker、APの役割と業務結果はAPログで確認します。一つの表示だけで「復旧した」と判断しないでください。

</details>

<details>
<summary>ヒント2：役割の変化と、その後の処理を比べる</summary>

昇格を示す行だけで判断せず、その後の業務に関する行を読みましょう。失敗を示す行があれば、どの処理で失敗したのか、メッセージの続きを確認してください。

</details>

<details>
<summary>答え合わせ：自分で考えてから、ログと照合する</summary>

以下は実装が出力するメッセージの固定部分です。日時や要求IDは実行ごとに異なるため、自分の画面のログを根拠に判断してください。

> `ap-server-2: PROMOTED to ACTIVE (failover)`

この記録は、AP2が待機系から現用系へ自動昇格したことを示します。ただし、業務の成功を示す記録ではありません。

> `DB connection failed:`

直近の業務ログにこの記録があれば、DBへの接続に失敗した要求があります。昇格していても、その要求は正常に業務を開始できていません。続く `worker=`・`request_id=` で要求を追い、`detail=` の説明を読みます。

> `job SUCCESS:`

これは業務成功の記録です。過去の成功行だけで復旧と判断せず、昇格後の直近の成功・失敗を確認しましょう。成功行が見えないことだけでは失敗の証拠にならないため、明示的な失敗行と区別します。

接続失敗の記録があれば、次の調査対象は接続先のPostgreSQLです。ただし、このログだけでは接続失敗の原因までは断定できません。Step 2でDB側の情報と照合しましょう。

</details>

## CHECK前の確認

- AP1、AP2、DBそれぞれのコンテナ状態を確認した。
- AP2の昇格記録と、直近の業務結果を区別して説明できる。
- 次に調べる対象を、ログを根拠に説明できる。

このStepのCHECKは、AP1がpause状態、AP2とDBが稼働中であることを判定します。ログからの読み取りは、自分でも確認してから進んでください。
