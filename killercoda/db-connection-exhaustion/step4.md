Step 3で業務は回復しましたが、現在の問題を解消した操作と、次の障害に備える仕組みは別です。同じ障害が再発した場合、人手の操作なしで回復できるでしょうか。

**調査・操作の目的：対策候補を比較し、設定の適用と実際の効果を区別して再試験で判断する。**

## 考える問題

1. 接続上限を増やすだけで十分でしょうか。`max_connections`、TCP Keepalive、`idle_in_transaction_session_timeout`、AP側のタイムアウト設計の役割を比較してください。
2. Step 2で観察した状態に対し、`idle_in_transaction_session_timeout` はなぜ有効と考えられますか。他の候補との違いと、正常業務へのリスクも考えてください。
3. 設定が表示されるだけで十分でしょうか。同じ障害を再現したとき、何を観察すれば効果を判断できますか。

自分の対策案と理由を整理してください。既存の演習用設定を適用する手順は模範解答にあります。再試験中は手動の接続終了やDB再起動を行わないでください。

<details>
<summary>模範解答：自分で考えてから開く</summary>

以下のコマンドを上から順に実行し、自分の出力と説明を照合してください。コードの実行ボタンは自分で押します。見つからないログや未観測の状態を、確認済みとして扱わないでください。

### 1. 対策を選ぶ

`idle in transaction` は、トランザクションを開いたまま要求を待つ状態でした。停止したAPの接続がこの状態で残る場合、何を検出して終了させればよいでしょうか。

| 候補 | できること | 限界・注意点 |
|---|---|---|
| `max_connections`の増加 | 同時接続の容量余力を増やす | 残留接続自体は解放せず、メモリなどの資源設計も必要 |
| TCP Keepalive | 応答がないTCP通信相手を検出する | 検出時間はOSや設定に依存し、応答する相手の無操作トランザクションを検出する機能ではない |
| `idle_in_transaction_session_timeout` | トランザクション中に要求を待ち続けるセッションを終了する | 通常のidle接続や、すべての障害条件を対象にするものではない |
| AP側の接続タイムアウト・再試行設計 | 接続待ちの時間や失敗後の再試行を制御する | それだけでDB側の残留接続を解放することはできない |

Step 2で観測した状態に対応するのは、どの候補でしょうか。容量の確保、異常検知、再試行の役割を区別して考えてください。

### 2. 今回の設定を理解して適用する

本演習では `idle_in_transaction_session_timeout = 30s` を採用します。トランザクションを開いたまま、クライアントからの次の要求を待つ状態が30秒続いたセッションをDB側で終了します。通常の `idle` 接続や、`active` 状態で実行中のSQLを、一律に30秒で終了する設定ではありません。

**30秒は演習専用の値です。** 正常なトランザクションでも待機が発生するため、短すぎる値は正常処理を誤って終了させます。本番へそのまま流用せず、業務上の待機時間やトランザクション設計から値を決めてください。この設定だけですべてのDB接続枯渇を防げるわけではありません。

```bash
cd /root/lab
/root/lab/scripts/apply-keepalive-setting.sh
docker exec db-server psql -X -P pager=off -U postgres -d appdb -c "SHOW idle_in_transaction_session_timeout;"
```{{exec}}

スクリプト名には `keepalive` が含まれますが、実際に適用するのは `idle_in_transaction_session_timeout` です。設定を書き込み、DB全体を再起動せずにリロードして反映します。`SHOW` の結果が `30s` であることを確認してください。ただし、設定値の確認だけでは、実際の障害時にも有効かは判断できません。

### 3. 同じ障害で再試験する

次のスクリプトは、環境の正常化・通常負荷の開始、通信遮断とAP1の一時停止、AP2の自動昇格の確認、接続数の時系列観測、AP2の業務回復確認を順に行います。正常化段階では古い接続の掃除やAPの再起動も行いますが、それを対策の効果とは扱いません。

障害を再現した後の自動解放を観察するため、再試験中に手動で `pg_terminate_backend` を実行したり、DBを再起動したりしないでください。スクリプトが終わるまで待ちます。

```bash
/root/lab/scripts/retest.sh
```{{exec}}

ログでは次を読み取ります。

- AP1由来の接続が観察され、時間経過で0本になったか。
- AP2の接続数がどう変化したか。
- `ap-server-2 の業務処理が回復しました` が表示されたか。
- 最後に `=== 再試験成功 ===` が表示されたか。

表示の `0秒` は**接続数の観察開始時点**で、障害投入時点ではありません。表示時間は10秒間隔の観察の目安で、厳密な障害発生からの経過時間ではありません。接続数や解放時間は変動するため、固定値を正解にしないでください。

「0秒時点で残留接続が0本」という警告が出た場合、自動解放の過程を観察できていない可能性があります。現行スクリプトはその後に成功を表示する場合がありますが、それだけで対策の有効性を確認済みとは扱いません。出力を記録し、再試験をもう一度実行して残留から解放まで観察できるか確認してください。繰り返す場合は未確認事項として残します。

### 判断と技術的な解説

以下は確認すべき結果と判断理由です。自分の設定値・再試験ログと照合し、観察できなかった内容を確認済みの事実にしないでください。

### 問1：接続上限の増加だけでは不十分な理由

**答え：max_connectionsを増やしても、残留接続が発生する仕組みは変わらないため。**

根拠は、Step 2の `pg_stat_activity` にAP1由来の接続が残っていたことです。`max_connections` は接続上限であり、接続を終了する条件ではありません。

増加は一時的な容量余力の確保にはなりますが、残留接続そのものを解放する対策ではありません。容量設計と残留接続の解消は、別の目的として検討します。

### 問2：今回の設定が有効な理由

**答え：今回の残留接続がidle in transaction状態だったため。**

根拠は、Step 2で確認したAP1の `pg_stat_activity.state` と、`SHOW` で確認した `idle_in_transaction_session_timeout = 30s` です。

この設定はトランザクション中の無操作セッションを一定時間後に終了するため、今回観察した状態に対応します。ただし、通常のidle接続や実行中のSQLを含む、あらゆる残留接続を解消する設定ではありません。

### 問3：対策の有効性を示す根拠

**答え：同じ障害を再現した際、AP1の残留接続が手動操作なしに解放され、AP2の業務が回復したこと。**

根拠として次を組み合わせます。

1. `SHOW` で設定値が `30s` である。
2. 再試験の時系列でAP1接続が残っている状態から0本へ変化した。
3. AP2の新しい業務成功を、業務回復確認ログで確認できた。
4. 最後に `=== 再試験成功 ===` が表示された。

設定値の適用と、実際の効果は別です。開始時点で既に0本だった場合は、2の証拠が不足しています。また、成功ログは今回の試験条件で有効だったことを示すもので、すべての障害条件での復旧を保証しません。

### まとめ

AP1由来の `idle in transaction` 接続が残留していました。接続上限を増やすだけでなく、今回の状態に対応するタイムアウトを導入し、同じ障害を再現します。その上で、AP1接続の自動解放とAP2の業務回復を観察して対策を評価します。
