業務は回復しましたが、同じ状況が起きても回復できる仕組みが必要です。Step 2で見た接続の状態を振り返り、対策と再試験を結び付けます。

**学習目標：暫定復旧と恒久対策を区別し、設定値だけでなく障害時の挙動で効果を確かめる。**

## 1. 対策を選ぶ

`idle in transaction` は、トランザクションを開いたまま要求を待つ状態でした。停止したAPの接続がこの状態で残る場合、何を検出して終了させればよいでしょうか。

| 候補 | 対応できること・限界 |
|---|---|
| `max_connections`を増やす | 接続余力は増えるが、残った接続自体は解消しない |
| TCP Keepalive | TCP通信の応答がない相手を検出する。検出時間はOSや設定に依存する |
| `idle_in_transaction_session_timeout` | トランザクション中に一定時間要求が来ない接続をDB側で終了する |
| AP側の接続タイムアウト・再試行設計 | 接続失敗時の待機や再試行を調整する。DB側の残留解消とは役割が異なる |

本演習では、観察した状態に対応する `idle_in_transaction_session_timeout = 30s` を採用します。SQL実行中の時間を一律に制限する設定ではありません。

## 2. 設定を適用して確認する

```bash
cd /root/lab
/root/lab/scripts/apply-keepalive-setting.sh
docker exec db-server psql -X -P pager=off -U postgres -d appdb -c "SHOW idle_in_transaction_session_timeout;"
```{{exec}}

スクリプト名には歴史的経緯で `keepalive` が残っていますが、実際に適用するのは上記のタイムアウトです。DB設定を書き込み、リロードして反映します。

**30秒は演習専用です。** 正常な業務でもトランザクションを開いたまま待機することがあります。本番へそのまま流用すると、正常処理まで切断するおそれがあります。実際の業務の待機時間・トランザクションの設計を調べ、値を決める必要があります。

## 3. 同じ障害で再試験する

次のスクリプトはAPと負荷を正常化し、障害投入・自動切替・接続数の観察・業務回復確認を実行します。途中で手動の接続終了や追加の復旧操作をせず、最後まで待ってください。

```bash
/root/lab/scripts/retest.sh
```{{exec}}

ログでは次を読み取ります。

- AP1由来の接続数がどう変化し、いつ0になったか。
- その後、AP2の業務回復を確認できたか。
- 最後に `再試験成功` が表示されたか。

表示の `0秒` は「接続数の観察開始時点」で、障害投入時点ではありません。解放時刻や接続数は実行ごとに変わるため、固定の数値を正解にしないでください。開始時点で既に0という警告が出た場合、その出力だけでは解放までの過程を観察できたとはいえません。警告も結果として記録してください。

## 出力から考えること

- 接続上限を増やす対策と、残留接続を解放する対策は何が違いますか。
- Step 3では自分が行った接続終了が、再試験ではどの仕組みによって行われましたか。

## CHECK前の確認

- 設定値が `30s` になっている。
- 再試験が完了し、AP1接続が0で、AP2の業務が回復している。
- 暫定復旧と恒久対策の違いを、観察結果を使って説明できる。

CHECKは設定値、再試験完了、AP1接続0、直近のAP2業務成功を判定します。警告を含む途中経過の評価は、自分の観察と合わせて行ってください。通過したらFinishへ進みます。
